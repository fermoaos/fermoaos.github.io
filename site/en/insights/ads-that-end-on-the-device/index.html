Advertising that ends inside the device

For anyone asked to deliver personalisation and privacy at once. While building an ad stack that infers intent on the device and sends no raw data out, we retracted the claim we had meant to win on. What remained was sturdier.

Sep 10, 2026

We retracted the claim that we win on accuracy

The pitch was going to be this: our 2.1MB on-device model beats a 421MB teacher once it gets behavioural data. There really was a measurement saying so. But it held in only one of four runs, the one with the smallest sample and the least favourable setup for the teacher. On real logs the teacher gained 12.8 points from behavioural data too. We dropped the claim.

Dropping it left a more accurate sentence. The moat is access, not accuracy. A server model would improve from these behavioural events as well. They simply never leave the device. That is not a performance race, it is a question of where the data sits, and so what we sell is not a prediction but a contract that nothing left.

The moment you sell a contract, the problem changes shape. Accuracy only has to improve. A contract has to be demonstrable.

A promise has to be a type, not a filter

Filtering out what must not leave, on the way out, eventually forgets to be called. So we left nowhere to put it. The struct that goes to the server has no string parameter anywhere in its public API, and unknown fields are rejected at parse time. The ad request struct has no field at all for a user id, an advertising id, an IP, or a user-agent string. It cannot leave because there is no slot to put it in.

The personal head, which is the whole point of personalisation, is bound harder still. In federated learning the server averages the projection matrix, while the personal head must never leave the device. Rather than writing that down as a rule, we built the inference core with zero dependencies. With no serialisation library available, there is no way to serialise the personal head at all. A type stops it, not a comment.

Behavioural events on the device follow the same idea. A test asserts that one event is exactly twelve bytes: a fixed-size value with no heap pointer and no string field, so raw text has nowhere to go. Even the battery level is recorded as one of four bands rather than a percentage, because a precise value is itself a fingerprint.

We still look at the bytes that actually leave

Saying a type prevents it is also just a claim. So the gate runs the real client binary, captures the payload as it was actually serialised, and inspects it. Do the top-level keys match the allowlist exactly, is none of the seven planted canary strings anywhere in the payload, is the size under the cap. Today’s run: six allowed keys, all seven canaries undetected, 69,482 bytes against a cap of 307,200.

An honest footnote. Seven canaries are a sample, not a proof; you do not get a proof of no leakage this way. What you do get is a check, every time, that the claim the types make still holds in the bytes. The ad request path carries the same check.

What publishing a budget means

Once the device population is large enough, federated learning turns on and the privacy budget is published. As measured today, per-round ε is 2.20 with a thousand participating devices, and a fifty-round campaign totals 1.73. What matters is the condition attached to the second number. It assumes subsampling amplification, meaning only a random subset of devices participates each round. Remove that assumption and the same campaign becomes 17.67, and the gate writes into its own output that the unamplified case is the unrealistic one. Quoting only the flattering number requires leaving the condition out.

The noise scale came from a sweep, not from taste. Smaller noise made the budget ten times worse while also ending at a worse loss, and larger noise diverged. Aggregation has a floor on participants, and the ad billing channel carries its own separate budget and a server-side suppression threshold.

There is a rule about the accounting itself, too. If the standard accounting library is unavailable, the gate reports unmeasured rather than computing it by hand, because subtly wrong accounting produces confidently wrong numbers.

This is how a less honest number survives

The failure we learned most from was an omission that flattered us. For a stretch, the SDK size gate was quietly excluding 206KB of taxonomy and affinity files from its count. The gate was green and the budget looked comfortable. What makes this class of omission especially dangerous is that the result favours you, so nobody goes looking. Bugs that hurt get caught quickly; bugs that help live a long time.

It happened once more in a different shape. A fast approximate judge reported a candidate model as a significant improvement four rounds running. Re-measured on the real deployment path with a paired bootstrap, the gain was less than half as large and its confidence interval crossed zero. That candidate did not ship. A judge being fast and a judge being right are separate claims.

When we promoted the model that is deployed now, we wrote down the price we actually paid. The product-surface metric rose by 0.87 points, and general language understanding fell by 1.21. That is roughly three times worse a trade than we had projected. We recorded it and promoted anyway.

What we cannot do yet

The deck said 4-bit 3B on-device LLM. Inside a 5MB budget that is impossible; a 4-bit 3B model is one and a half to two gigabytes. So it split into two tiers. What always runs is the small zero-dependency static embedding; the large model is an optional tier that borrows what the operating system already ships. And in the current demo that optional tier is a tunnel to an internal GPU host, not a real on-device model. We do not describe it as running on the device.

Latency is a p95 of 2.85 milliseconds on a development Mac. We have not measured a low-end Android yet, and there are no Android resident-memory or battery figures. The real exchange is not connected; only a mock server exists. The affinity file is synthetic. We work in the order that shortens this list.

That is everything we can currently say. A company selling personalisation is better off showing its own list of limits first than having the customer find that list later.
